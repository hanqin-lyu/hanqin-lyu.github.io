M365 account compromise and BEC investigation lab

The endpoint lab covers investigating a host. This one covers the other incident a SOC analyst is asked about most: a compromised Microsoft 365 account and the business email compromise that follows – investigated from the alert, contained, hardened and written up for a client.

Microsoft 365 E5 Microsoft Defender XDR Entra ID BEC OAuth Consent Incident Report
Planning · GitHub repository

The incident

One compromise, run as a single story in a Microsoft 365 E5 trial tenant. The victim is a finance user: a standard account with no admin role, but one that can make money move.

StepWhat happens
1A phishing campaign reaches several users: the finance user clicks a credential-phishing link; a colleague's version with an attachment (the EICAR test file) is blocked
2Unusual sign-in to the account
3Persistence: signed in as the user, the attacker consents to an app with mailbox access, so access survives a password reset
4Inbox rule that forwards mail outside the organisation
5From the finance mailbox, the attacker sends a bank-details change request to a lab "supplier" and phishing to colleagues

Scope. Step 1 is scoped as a campaign – who else got it, what verdict each message got, whether it was removed after delivery – and stays on the email side; an attachment opened on a device is endpoint work. Impersonation BEC from lookalike domains is not simulated and appears only as a hardening recommendation.

Five problems it has to solve

Each part of the investigation and response serves one of these, and each is answered with evidence from the tenant.

  • A password reset does not end the compromise The OAuth consent grant, the inbox rule and tokens already issued keep working. Containment runs in order – revoke sessions, reset the password, remove the inbox rule, revoke the app's consent grant – and a re-test shows each attacker foothold is rejected.
  • A forwarding rule moves mail out unseen The rule is found, tied to the session that created it, and the mail it forwarded is counted.
  • The client needs to know what was read Purview Audit MailItemsAccessed scopes what the attacker read. The report states what was accessed and the evidence for it, as input to the client's decision on notification, for example under Australia's Notifiable Data Breaches scheme.
  • Mail from a real finance mailbox is trusted A bank-details change request or a link to colleagues looks legitimate. Every fraud and phishing email is traced to its recipients and clicks, the delivered messages are removed, and the report names who must be warned before money moves.
  • Nobody checks whether the attacker reached admin rights A privilege check with evidence – role assignments, admin consent, new app credentials, mail flow rule changes – and a report section on how the response would differ for an admin account.

Recovery and the people side

BEC destroys nothing, so recovery is about the money, the mail, the account and the people – and users are part of both detection and prevention.

  • Funds The bank's fraud team is called at once and the case reported to ReportCyber. No money moves in the lab, so this is written as the procedure and when it would start.
  • Mail and account Supplier replies hidden by the inbox rule are restored, and a re-test shows the account has no attacker sessions, app grants, rules or MFA methods left.
  • User reporting Colleagues report the phishing with the built-in Report button; the investigation records whether a user report or an automatic alert came first.
  • Training and process Attack simulation training copies the real lures after the incident. For finance, the fix is a process rule: bank-detail changes are confirmed by calling a number already on file. The lab has only a few test users, so the numbers show the mechanism, not a workforce.

Design decisions

Written down before building, so the claims stay honest.

  • Real telemetry only Every alert, timestamp and screenshot comes from my own trial tenant. No synthetic logs.
  • Investigate from the alert The investigation starts in the Defender portal from what fired, not from the simulation notes.
  • Two certifications, one incident The investigation uses SC-200 skills; the containment and hardening use SC-300 skills.
  • Same fictional client as the endpoint lab Both investigations are written for one client, so the two reports read as one engagement.

Deliverables. An investigation walkthrough, a record of the containment and hardening actions, a recovery record, a user training record, and a client-facing post-incident report that compares the response for a standard and an admin account. The client is fictional; the data is not.

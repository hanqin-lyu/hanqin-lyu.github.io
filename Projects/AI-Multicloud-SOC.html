Multi-cloud SOC: cross-cloud identity investigation

The closed-loop SOC stops an unknown attacker at the edge of one VM. This project follows an attacker who already has valid credentials: one stolen identity moves from Entra ID into Azure, into AWS through federation, and onto a machine. The work is joining the pieces into one incident, working out the blast radius, and containing it in both clouds.

Three problems it has to solve

Each feature has to serve one of these, and each has a metric measured from real runs.

  • The attack is seen in pieces Entra sign-ins, Azure activity, CloudTrail and host logs sit apart, so each alert looks small. All sources land in one workspace, every rule maps the same account entity, and a correlation rule joins the steps into one incident. Target: one incident per chain run.
  • Nobody can say what the identity could reach The blast radius is answered in two columns: what the identity could reach, from a read-only permission listing across Entra ID, Azure and IAM Identity Center, and what it did touch, from the logs. The gap between them drives the hardening recommendations.
  • Containing one cloud leaves the other open Disabling the Entra user does not end an AWS session that was already issued. One ordered playbook, approved by the analyst, contains the identity in Entra ID and AWS, isolates the host and rotates the exposed secret — then a re-test checks that every attacker session and key is rejected.

Re-scoped before building. The first draft was an EU honeypot with data residency, two regional workspaces, threat-intelligence feeds and automatic IP blocking in both clouds. It mostly repeated the baseline at a larger size and showed automation rather than investigation, so it was cut back to one end-to-end identity story. ML stays as per-identity anomaly detection; an anomaly raises severity but never decides an incident or a response.

AI-Assisted, Multi-Cloud SOC

The follow-on to the Sentinel closed-loop SOC. That project is the manual, rule-based baseline; this one adds ML-based anomaly detection, threat hunting, and log collection across both Azure and AWS — with the first project's measured response times kept as the number to beat.

Scoping in progress · Builds on the closed-loop SOC

What changes from the first project

The closed-loop SOC proved a manual, rule-based loop end to end. This project keeps that loop as the baseline and raises each part of it.

Things to settle first

Open questions being written down before any building starts — the same honest-scoping habit as the first project.

  • AWS needs Azure Arc Azure Policy only reaches AWS machines once they are onboarded to Azure Arc. Microsoft's built-in policies then install the Azure Monitor Agent and associate a data collection rule on the Arc-enabled servers, using each machine's system-assigned managed identity. Onboarding to Arc comes first.
  • What "the ML does" has to be defined Detection here means ML anomaly detection — for example UEBA and the KQL time-series anomaly functions — which is a different approach from having an AI draft KQL rules. The exact scope gets written down before building so the claims stay honest.
  • Keep the first project's numbers as the baseline The closed-loop SOC's workbook already measures time to acknowledge, time to contain and approval latency. Those numbers are the comparison point this project has to improve on.

Out of scope for the first project, on purpose. AI/ML analysis, threat hunting and multi-cloud collection were deliberately kept out of the closed-loop SOC so that project could stay a clean, provable baseline. They are the whole point of this one.
